# Brandtree dogfood site

This is the example brand-guidelines site maintained with the Brandtree framework.
It uses the same authoring contract and CLI as a consumer project, with English
and Arabic content, local fonts, photography, and an explicitly maintained icon set.

For the framework introduction and CLI guide, see the [repository README](../../README.md).

## Run locally

Run these commands from the repository root. Requires Node.js 22.12+ and pnpm 11.18.

```sh
pnpm install
pnpm dev
```

The root development, build, and deployment scripts build the framework package
before invoking the site. Direct `pnpm --filter web ...` commands require
`pnpm --filter brandtree build` first.

| Command        | Action                                                                             |
| -------------- | ---------------------------------------------------------------------------------- |
| `pnpm dev`     | Start the site on `localhost:4321`                                                 |
| `pnpm build`   | Build static output to `apps/web/dist/`                                            |
| `pnpm check`   | Check framework and site types; requires the forthcoming `brandtree check` command |
| `pnpm preview` | Serve the built site; requires the forthcoming `brandtree preview` command         |
| `pnpm deploy`  | Build and deploy the site to Cloudflare                                            |

The CLI check and preview implementations belong to separate prerequisite PRs.

## Project files

Paths below are relative to this app.

| Path                    | Purpose                                                                             |
| ----------------------- | ----------------------------------------------------------------------------------- |
| `brandtree.config.ts`   | Structured brand data, themes, fonts, locales, navigation, and social-card settings |
| `content/{en,ar}/`      | Localized MDX prose and folder metadata                                             |
| `assets/fonts/`         | Licensed local font files                                                           |
| `assets/photography/`   | Explicitly imported photographs and their credits                                   |
| `assets/icons/index.ts` | Shared SVG imports and icon records used by both locales                            |
| `public/`               | Artwork and other files served unchanged                                            |
| `.brandtree/`           | Disposable Astro runtime generated by Brandtree                                     |
| `dist/`                 | Generated static site                                                               |

Keep authored work outside `.brandtree/`; the CLI recreates that directory.

## Customize the site

1. **Rename the deployment.** Set the Cloudflare Worker `name` in
   `wrangler.jsonc`; workspace package names remain stable.
2. **Fill in [`brandtree.config.ts`](brandtree.config.ts).**
   Put name, palette, type scale, logo paths, and contact under `config.brand`;
   configure site behavior with `config.i18n` and `config.navigation`.
   Everything else reads from this parsed configuration. Colour `id`s become
   `--color-{id}` and are referenced by `theme` — keep them stable while you
   change names and hex values. Unknown keys and invalid cross-references fail
   validation at the configuration boundary.
3. **Drop in the artwork.** Replace the four placeholder SVGs in
   [`public/brand/`](public/brand/) and `public/favicon.svg`. Convert wordmark
   type to outlines. Keep each file single-colour — `LogoColorways` recolours
   the mark with a CSS mask, which only works on flat artwork.
4. **Set the typefaces.** Edit the `fonts` block in
   [`brandtree.config.ts`](brandtree.config.ts). Self-host a licensed file from
   `assets/fonts/`, or switch `provider` to `"google"` and
   drop `options`. Whatever `cssVariable` you use must match
   `typography.display` / `typography.text` in the brand config. Use the same
   loading declarations for Brandtree CLI consumers.
   Generated social cards reuse Astro's resolved local and Google font files and
   the locale's display/text families, without a separate OG loading list.
   Astro resolves Google Inter when font declarations are omitted or a local
   font declaration is removed because its files are unavailable. Inter does not
   cover all languages; provide a working font with
   the script coverage your cards require.
5. **Rewrite the sections.** Content in
   [`content/`](content/) is organized by locale. A
   numbered file is a top-level page; a numbered folder is a navigation group
   whose `index.mdx` is its overview and whose child files become nested pages.
   Delete a page or group and it disappears from the nav, contents list and
   prev/next pager — sibling ordering follows numeric prefixes automatically.
6. **Swap the imagery.** Replace `assets/photography/` (see its
   `CREDITS.md` — the samples are Unsplash placeholders) and
   `assets/icons/`. Maintain the explicit SVG imports and icon records
   in `assets/icons/index.ts`; both localized iconography pages import
   that shared inventory and pass it to `IconGrid`.
7. **Check it.** `pnpm check` for types, `pnpm build` for the real thing.
8. **Ship it.** `pnpm deploy`.

## Brand configuration

Parsed with the strict Zod schemas in [`packages/brandtree/src/brand/schema.ts`](../../packages/brandtree/src/brand/schema.ts).
The inferred types in [`packages/brandtree/src/brand/schema.ts`](../../packages/brandtree/src/brand/schema.ts) keep editor
autocomplete aligned with the runtime model, and the build fails on unknown
keys, duplicate identities, or unresolved references rather than rendering a
blank swatch.

This excerpt illustrates the configuration shape; use the complete
[`brandtree.config.ts`](brandtree.config.ts) as the starting point.

```ts
import { defineConfig } from "brandtree";

export default defineConfig({
  brand: {
    colors: {
      palette: [
        {
          id: "orange",
          name: "Orange",
          shades: {
            50: { space: "hex", value: "#fff3ed" },
            500: { space: "hex", value: "#ef3800" },
            950: { space: "hex", value: "#3b1000" },
          },
        },
      ],
      swatches: [
        {
          id: "orange-red",
          name: "Orange/Red",
          color: "orange-500",
          category: "secondary",
        },
      ],
    },
    theme: {
      default: "system",
      light: {
        background: "white",
        foreground: "black",
        primary: "orange-500" /* … */,
      },
      dark: {
        background: "black",
        foreground: "white",
        primary: "orange-500" /* … */,
      },
    },
    localeOverrides: {
      ar: { meta: { documentTitle: "دليل الهوية" } },
    },
  },
  i18n: {
    defaultLocale: "en",
    locales: [
      { code: "en", label: "English" },
      { code: "ar", label: "العربية", dir: "rtl" },
    ],
  },
  navigation: {
    numbering: true,
  },
});
```

`config.i18n.locales` order controls only the language switcher's display
order; locale lookup is by `code`. `defaultLocale` must match one configured code.
The `dir` value defaults to `ltr`; set `rtl` explicitly for right-to-left
locales. Omitting `i18n` creates a single-locale site without locale segments in routes. Template UI dictionaries are supplied by the
template, not by client config. The English baseline is derived from the UI
schema; the bundled Arabic UI pack is a sparse override. UI resolution layers
English, the configured default locale's built-in pack, and the requested
locale's built-in pack. Pack lookup tries exact code, case-insensitive exact
code, then base language. The client-authored
`config.brand.localeOverrides` block remains the separate, exact-code
brand-content override layer described in ADR 0003 and ADR 0005.

`config.navigation.numbering` is presentational only: it adds ordinal labels
without changing section order, route identity, filenames, or the future
project tree. Navigation structure and ordering continue to come from the
content tree and section metadata.

Roles map onto stable shade references, and components only ever reference the
role — so the underlying source values can be Hex or OKLCH without changing
the UI contract. `black` and `white` are built-in colour tokens, available to
swatches and theme roles without palette entries.

Open Graph cards are generated at build time for every cover and content route
using each page's title and resolved description (`seo.description` wins over
`description`). Their eyebrow defaults to the localized site title, their
subtitle falls back to the brand description, their footer uses the site host,
and their palette comes from the configured light brand theme. Configure the
outlined SVG and fonts under `config.seo.og`; `eyebrow`, `description`, `logo`,
and `site` accept an override string or `false` to hide that layer. Set
`enabled: false` to disable generated cards. A frontmatter `seo.image` still
supplies that page's card—using either a file in `public/` or an external
URL—even when generation is disabled. Generated cards are 1200×630 PNGs at
`/og/<route>.png`, and their complete Open Graph and X metadata is emitted
automatically.

## Content authoring

The `NN-` prefix sets the order and the printed section number; the URL uses the
slug without the prefix (`en/03-logo/index.mdx` → `/en/logo`). Frontmatter is validated by
[`pageMetaSchema`](../../packages/brandtree/src/core/schema.ts) through the generated collection:

```mdx
---
title: Colour
description: Two colour families, one signal colour, and the ratios that hold them together.
---

<Block>
<Fragment slot="copy">

## Colour

### Palette

Two colour families, one signal colour, and the ratios that hold them together.

</Fragment>

<Fragment slot="content">

<ColorPalette brand={props.brand} ui={props.ui} />

</Fragment>

<Fragment slot="note">

Black and white carry the work. The accent is the exception, not the rule.

</Fragment>
</Block>
```

`Block` is the document's core layout. Its named slots are:

- `copy` — the block's Markdown/MDX richtext, including its heading,
  subheading, and any supporting paragraphs.
- `content` — rich component content such as an image gallery, type scale
  chart, colour palette, or specimen.
- `note` — optional secondary Markdown/MDX copy.

Use `Block` for split layouts only. It places the `copy` and `note` in a side
column beside the `content`; keep structural headings in the `copy` slot so
they remain native Markdown/MDX headings and can be included in the page
contents outline. The named slots are the API for that layout, not a
general-purpose wrapper.

For regular grouped content, write the headings, copy, and components directly
in the MDX flow. This keeps one subject together without creating multiple
split blocks:

```mdx
## Logotype

### Primary logo

The primary logo is a logotype. Always place the supplied artwork.

<Panel brand={props.brand} ratio="16 / 9">
  <Logo brand={props.brand} mark="logotype" width="66%" />
</Panel>

### On black

On dark surfaces the logotype reverses to white.

<Panel brand={props.brand} bg="black" ratio="16 / 9">
  <Logo brand={props.brand} mark="logotype" on="dark" width="66%" />
</Panel>
```

The frontmatter `description` becomes the standfirst on the section divider.
Set `draft: true` to keep a page visible in `dev` but out of the build.

### Nested groups

Use a folder when one topic needs an overview and several related pages. The
folder name and numeric prefix determine its URL and sibling order; `index.mdx`
is the group landing page and `meta.ts` is optional localized navigation
metadata:

```
content/en/03-logo/
├── meta.ts
├── index.mdx
├── 01-logotype.mdx
├── 02-brandmark.mdx
└── 03-usage-rules.mdx
```

`meta.ts` must use a static `defineMeta` call. Its `pages` array orders direct
children by their normalized slugs. Page `icon`, page `sidebar.icon`, and folder
`icon` fields are strings resolved against the bundled Phosphor collection.
For pages, `sidebar.icon` overrides the top-level `icon` in navigation.
Use kebab-case names such as `book-open`, `acorn`, `folder-simple`, or `text-aa`.
Unknown names render no icon.
Icons come from Iconify's bundled `@iconify-json/ph` collection. Names are trimmed
and lowercased; `rocket` and `ph:rocket` resolve identically. Iconify aliases and
weight suffixes such as `rocket-bold` are supported.

```ts
import { defineMeta } from "brandtree";

export default defineMeta({
  title: "Logo",
  icon: "shapes",
  order: 3,
  pages: ["logotype", "brandmark", "usage-rules"],
});
```

Metadata is locale-specific, so an Arabic group can translate its title and
choose its own child ordering. Nested MDX files use the same centrally provided
components as top-level pages; their directory depth does not affect component
availability.

## Components

Brand guideline MDX files can use built-in components directly. Brandtree's generated
route supplies `brandtree/components` through the MDX `components` prop. Brand-aware
components receive `brand={props.brand}` and UI-aware components receive
`ui={props.ui}`. Import custom components explicitly from the author-owned
`components/` directory; there is no app-specific component barrel.

**Layout** — `Block` (split layouts with `copy`, `note`, and `content` slots),
`Statement` (the one oversized paragraph that carries a page), `Grid`, `Panel`,
`Figure`, `SpecList`, `Callout`. For grouped content without a split layout, use
normal MDX flow rather than wrapping it in `Block`.

**Colour** — `ColorPalette`, `ColorScale` (config-defined Tailwind-style
shades), `ColorSwatch`, `ContrastMatrix` (every pairing measured against WCAG,
failures struck through).

**Type** — `TypeSpecimen`, `FontWeights`, `Glyphs`, `TypeScale` (renders each
step at its real size beside its spec).

**Logo** — `Logo`, `LogoColorways`, `LogoScaling`, `LogoClearspace`,
`LogoMisuse`, `ConstructionGrid`.

**Everything else** — `IconGrid`, `PhotoGrid`, `LayoutGrid`, `ValueGrid`,
`PersonaCard`, `ToneSliders`, `Downloads`.

`Figure` renders a labelled placeholder frame when you give it no `src`, so
application pages read correctly before the client's mockups exist.

## Routes and languages

Both English and Arabic use a visible locale prefix. The same section structure
is available under `/en/` and `/ar/`:

```text
/{locale}/                  cover and contents
/{locale}/the-brand         purpose, mission, vision, values, audience
/{locale}/tone-and-voice    tone and writing rules
/{locale}/logo              logo overview
/{locale}/logo/logotype     logotype artwork
/{locale}/logo/brandmark    brandmark and construction grid
/{locale}/logo/usage-rules  clear space, colourways, scale, misuse
/{locale}/colour            palette, proportions, contrast
/{locale}/typography        specimens, weights, glyphs, type scale
/{locale}/iconography       icon set and grid
/{locale}/photography       light, dark, duotone treatments
/{locale}/layout            web, social, print grids
/{locale}/digital           website, favicon, app icon, social
/{locale}/print             stationery, posters, promotional, signage
```

The `/` entry page reads the saved-language cookie in the browser and redirects
to the selected locale. With JavaScript disabled it redirects to the configured
default locale. Arabic pages use right-to-left layout and localized brand values.
Light and dark themes work without JavaScript.

## Deployment

The site produces static HTML, optimized images, scripts, styles, fonts, and
social cards in `dist/`. It can be hosted on any static host.

For Cloudflare, set the deployment name in [`wrangler.jsonc`](wrangler.jsonc),
then run `pnpm deploy` from the repository root. Cloudflare serves `dist/`
directly; this app does not deploy an Astro server entry point or an asset binding.
A dry run checks the deployment configuration without publishing:

```sh
pnpm --filter web exec wrangler deploy --dry-run
```
